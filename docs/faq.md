# FAQ / 常见问题

## 是否必须使用很多员工？

不需要。员工数量由任务的专业跨度决定。一个小修改直接找一个员工更快；只有跨专业任务才动态组队。

## 最少需要哪些员工？

MakeCrew 的基础闭环是 `CEO-001`、`PM-001` 和 `QA-001` 三个核心岗位。开发、研究、内容、设计、知识库、Skill 开发等都是可选模板，用户按项目自行增加、复制或暂不启用。

## 如何增加自己的员工？

运行 `makecrew add-employee`，填写唯一 ID、岗位名称、Skill、工具和记忆范围。注册是增量操作，不覆盖核心岗位、已有员工或项目记忆。

## CEO 会不会变成新的瓶颈？

路由规则要求单岗位任务绕过 CEO。CEO 只处理跨项目方向、资源冲突和重大交付。

## CEO 批量调度会多消耗很多 Token 吗？

会增加一次规划、派发和汇总的模型调用。五个很短的小任务手动直达员工通常更省；五个复杂任务或有依赖的任务，CEO 的额外管理成本通常小于重复背景、顺序混乱和返工成本。`BatchScheduler` 本地状态计算本身不调用模型。

## 对外介绍时能说 CEO 调度几乎没有成本吗？

不建议这样表述。更准确的说法是：CEO 调度有少量管理 Token 成本，换来并行执行、依赖管理、员工线程复用和统一验收；用户可以按任务规模选择手动派发或批量模式。

## 为什么计划出来了却没有员工执行？

`route_task()` 只生成计划；`CrewOrchestrator` 才负责派单。没有宿主平台
dispatcher 时，结果状态是 `queued`，表示等待连接执行器。接入 dispatcher
后才会把最小任务包发送给注册表中的员工，并返回员工结果；CEO 不代替员工执行。

## 单任务为什么不经过 CEO？

单任务最省 Token 的路径是在当前对话内完成需求澄清、工具规划和执行。
只有多任务并发、跨项目资源冲突或明确要求 CEO 批量调度时，才启用 CEO。

## 新对话遇到模糊需求会怎么处理？

先问最多三个会影响结果的关键问题；需求清楚后，再从本地目录或宿主搜索器发现相关方法、工作流和 Skill，列出适用场景、证据与取舍。用户选择并确认后，才在当前对话执行。搜索结果不会自动安装 Skill 或改变任务范围。

## 长期项目如何保持记忆？

项目上下文包保存稳定信息，长期员工保留自己的对话；主管通过差量交接同步新增决策和状态。

## 如何避免员工互相重复工作？

任务卡设置唯一负责人、协作者、依赖和交付物。主管派发前检查看板中是否已有同类任务。

## 多个任务如何并发又不失控？

显式使用 `BatchScheduler` 登记每项任务和 `depends_on`，再设置
`max_concurrency` 与 `total_tool_calls`。独立任务并行，后置任务等依赖完成，
超预算任务进入等待状态。可以暂停、恢复、取消或记录失败，状态和原因都保留。

## 每个批次都会新建员工对话吗？

不会。调度器按 `(employee_id, project)` 复用线程；只有注册表没有匹配岗位时才创建临时员工或新对话。单任务仍留在当前对话，不经过 CEO。

## 什么时候让用户确认？

高成本制作、公开发布、不可逆操作、涉及预算或方向选择时先给方案/预览。普通低风险内部步骤可以直接执行。

## 如何衡量是否有效？

比较同类任务的总耗时、返工次数、重复说明次数、工具调用次数、交付质量和可复用程度。员工数量本身不是指标。

## 私有资料如何处理？

把真实对话、密钥、账号、客户资料和本地路径放在私有存储；公开仓库只保留通用模板和虚拟示例。
